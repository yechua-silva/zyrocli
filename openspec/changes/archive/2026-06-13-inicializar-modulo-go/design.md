# Design: Inicializar módulo Go y estructura base del proyecto

## Technical Approach

Create a compilable Go scaffold in a single pass: `go.mod` → deps → `cmd/zyrocli/main.go` (Cobra root) → 7 internal packages with compilable stubs → config files. All stubs use stdlib-only imports with exported types or functions containing `// TODO` markers. Verification via `go vet ./...` and `go build ./...` at the end.

## Architecture Decisions

### Decision: Cobra root command with persistent flags

**Choice**: Single `cmd/zyrocli/main.go` with `rootCmd` struct, `Execute()`, and `init()` registering `--verbose` persistent flag. No subcommands registered yet — stubs only.
**Alternatives**: Multiple entry points (`cmd/zyrocli/*.go` per subcommand) — premature for scaffold phase.
**Rationale**: Matches AGENT.md structure. Persistent flags on root propagate to all future subcommands. Single file keeps initial complexity near zero.

### Decision: Flat internal/ packages (no nesting)

**Choice**: `internal/{scheduler,handoff,skilladvisor,spec,context,apply,test}/` — flat, one domain per directory.
**Alternatives**: Nested (`internal/core/`, `internal/integrations/`) — adds path complexity for 7 small packages.
**Rationale**: AGENT.md defines these exact 7 domains. Flat layout matches the mental model. When a package grows, it can be reorganized later without affecting callers.

### Decision: Dependencies — cobra + yaml.v3 only

**Choice**: `github.com/spf13/cobra` and `gopkg.in/yaml.v3` as first external deps.
**Alternatives**: `viper` for config — unnecessary until real config loading exists. `encoding/json` stdlib — insufficient for YAML handoff parsing.
**Rationale**: Cobra is the CLI standard (used by kubectl, gh, hugo). yaml.v3 is the de facto YAML library for Go. Both are stable, well-maintained, and match AGENT.md's stated stack.

### Decision: Compilable stubs vs empty files

**Choice**: Each stub file has `package` declaration, at least one exported type or function, and `// TODO` comment explaining future implementation.
**Alternatives**: Empty `.go` files — won't compile (no exported symbols = unused package risk).
**Rationale**: `go build ./...` must pass in this change. Stubs with exported symbols prove the package is importable. TODOs serve as breadcrumbs for sdd-apply.

## Data Flow

```
cmd/zyrocli/main.go
  ├── imports internal/scheduler
  ├── imports internal/handoff
  ├── imports internal/skilladvisor
  ├── imports internal/spec
  ├── imports internal/context
  ├── imports internal/apply
  └── imports internal/test
        │
        └── main() → rootCmd.Execute()
```

No runtime data flow in this change — all packages export stubs only. Real data flow begins when sdd-apply implements business logic.

## Testing Strategy

| Layer | What to Test | Approach |
|-------|-------------|----------|
| Unit | Not in this change | Stubs only; tests begin in sdd-apply |
| Integration | `go vet` and `go build` pass | Verification step in sdd-apply or sdd-verify |
| E2E | `zyrocli --help` prints root command | Manual verification after build |

No tests written in this change. Test infrastructure documented for future phases: table-driven tests per go-testing skill, `t.TempDir()` for filesystem tests, integration tests skippable with `testing.Short()`.

## Migration / Rollout

No migration required. This is a greenfield scaffold — no existing code or data to migrate.
